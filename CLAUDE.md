## What this is

VELA — a Spanish-language event marketplace (React + Vite SPA on the frontend, Supabase for auth/db/storage/edge functions). Attendees discover and buy tickets (`boletos`) for events (`eventos`); hosts (`anfitriones`) create events and get paid out via Mercado Pago. Deployed to Vercel (SPA rewrite in `vercel.json`).

**Dominio oficial: `https://www.velaapp.online`** — es la URL real del producto y la única que se usa para probar. El apex (`velaapp.online`) redirige ahí con un 308. La vieja URL de Vercel (`eventapp-flax.vercel.app`) sigue viva y sirve el mismo deploy, pero **no** es el sitio oficial; solo se conserva como respaldo de pruebas.

Cuidado: hay tres lugares que necesitan conocer el dominio y no se enteran solos — la lista blanca de CORS de las Edge Functions (`supabase/functions/_shared/cors.ts`), el secreto `SITE_URL` de Supabase (a dónde vuelve el comprador tras pagar en MP) y *Authentication → URL Configuration* en el dashboard de Supabase (Site URL + Redirect URLs, de lo que depende el login con Google). Si alguna vez cambia el dominio, hay que tocar los tres o partes enteras de la app dejan de funcionar en silencio.

## Architecture

**Single-file pages, no shared UI kit.** Everything lives in `src/pages/*.jsx` — each page is one large component file with inline `style={{...}}` objects (no CSS modules/styled-components/Tailwind classes in JS, even though Tailwind is a dependency). There's no component library. When editing a page, expect the whole page (layout, data fetching, forms, modals) in one file — `PanelAnfitrion.jsx` (~790 lines) and `Evento.jsx` (~555 lines) are the largest.

**Routing** is centralized in `src/App.jsx`, which also contains the entire logged-out/logged-in home page (`HomePage`) inline plus global auth state (`user`, `perfil` from the `profiles` table) fed via `supabase.auth.onAuthStateChange`. All routes are declared in one `<Routes>` block there — add new pages both as a file in `src/pages/` and a `<Route>` in `App.jsx`.

**Supabase is the backend.** `src/supabase.js` creates the client (publishable key is hardcoded there, not a secret — RLS enforces access control). Prefer `getUserSafe()` from that file over raw `supabase.auth.getUser()` for anything that gates page rendering: `getUser()` makes a network round-trip with no built-in timeout and can hang a page in a loading state indefinitely (especially right after a mobile app resumes from background); `getUserSafe()` races it against a short timeout and falls back to the cached local session.

**Data access pattern:** pages query Supabase tables directly with the JS client (`supabase.from(...).select(...)`), often joined (e.g. `eventos` joined with `profiles` and `boletos`). `@tanstack/react-query` is used for caching/loading state on read queries (see `HomePage`'s `eventos` query in `App.jsx`). Row-Level Security in Postgres is the real authorization boundary, not frontend checks — `es_admin` / `tipo` / `estado_anfitrion` flags on `profiles` gate UI visibility only.

**Privileged operations go through Supabase Edge Functions** (`supabase/functions/*/index.ts`, Deno), called from pages via plain `fetch` to `${VITE_SUPABASE_URL}/functions/v1/<name>` with the user's JWT as a Bearer token — not `supabase.functions.invoke`. Each function creates its own `service_role` Supabase client server-side. Use an edge function (not a direct table write) whenever an operation needs to: touch a secret (Mercado Pago host token, refunds), act across a permission boundary (host approving/rejecting another user's ticket request), or needs custom rate limiting — functions manually rate-limit via a `rate_limits` table (see `crear-pago-mp` and `gestionar-solicitud` for the pattern: count rows in the last hour window, insert one row per call, reject over a threshold).

Current functions: `crear-pago-mp` (creates an MP checkout preference, looks up the host's `mp_access_token`, applies a 10% marketplace fee), `confirmar-pago-mp` (verifies a completed payment directly against the MP API using the host's token, then activates the boleto — called from `PagoExitoso.jsx` instead of trusting the `collection_status` return URL param), `gestionar-solicitud` (host approves/rejects a requested ticket, triggers MP refund on reject), `hacer-checkin` (host marks a boleto as checked in; validates ownership, `estado = "activo"`, and blocks double check-in), `cancelar-evento`, `eliminar-cuenta`, `guardar-resena`, `reportar-evento`, `resolver-reporte`, `mp-oauth` (OAuth flow for hosts connecting their Mercado Pago account).

Note: `supabase/config.toml` is now accurate and authoritative (2026-07-09). It declares `verify_jwt = false` for exactly the public functions (`mp-webhook`, `mp-oauth`, `unirse-cooperador`, `buscar-checkin-cooperador`, `guardar-avatar-registro`); every other function uses the default `verify_jwt = true` and requires a valid user JWT. The old phantom entries (`crear-preferencia`, `webhook-pago`, `crear-pago-stripe`, `stripe-connect-onboarding`) were removed from `config.toml` **and** deleted from the Supabase project. The project migrated from Stripe to Mercado Pago; Stripe packages were removed from `package.json` entirely (2026-07-09). **Important lesson (learned the hard way):** if you `supabase functions deploy` a public function, its `config.toml` entry MUST exist first — deploying without it flips `verify_jwt` back to `true` at the gateway and silently breaks the MP webhook/OAuth (their callers don't send a JWT).

**Payments:** Mercado Pago only (Stripe SDKs were removed from `package.json` on 2026-07-09; the project had migrated off Stripe long before). Two ticket flows exist per event (`tipo_boleto`): `instantaneo` (ticket activates immediately on payment) vs solicitud/request-based (host must approve via `gestionar-solicitud` before the ticket is `activo`). Boleto states include `activo`, `rechazado`, and pending/requested states — check `boletos.estado` before assuming a ticket is valid.

**Env vars** (`.env`, Vite-prefixed): `VITE_MP_CLIENT_ID`, `VITE_SUPABASE_URL`. Edge functions use their own Deno env vars (`SUPABASE_URL`, `SERVICE_ROLE_KEY`, `MP_ACCESS_TOKEN`, `MP_CLIENT_ID`, `SITE_URL`) configured in the Supabase project, not `.env`.

**Language:** all UI copy, route paths, DB table/column names, and most code comments are in Spanish (e.g. `/mis-boletos`, `eventos`, `boletos`, `anfitrion`). Keep new code consistent with this — don't introduce English table/column names or route paths.

Al aprobar uno y rechazar el otro, el rechazo reembolsó el pago compartido completo (el monto coincidía con el total pagado), dejando el boleto aprobado "activo" con un pago ya reembolsado. **Corregido:** `Evento.jsx` borra cualquier `pendiente_pago` sobrante del mismo usuario+evento justo antes de insertar los boletos de un nuevo intento de compra (mismo criterio ya usado por la política RLS de `DELETE` en `boletos` para pendientes abandonados) — con eso nunca puede haber más de un lote de pendientes por usuario+evento a la vez, así que la activación por lote de `confirmar-pago-mp` vuelve a ser correcta. **El reembolso en sí (`gestionar-solicitud`) se confirmó funcionando correctamente con dinero real** — el pago pasó de `approved` a `refunded` verificado contra la API de MP; el problema era el boleto duplicado antes del reembolso, no el reembolso. **Pendiente real, deliberadamente no resuelto todavía:** si un pago queda `in_process`/`deferred_retry` y el banco lo aprueba horas después, hoy nada vuelve a preguntarle a MP — el boleto de ese intento se queda huérfano en `pendiente_pago` (invisible, inofensivo, pero el comprador se queda sin boleto aunque el banco sí cobre). **Resuelto (2026-07-04):** nueva Edge Function `mp-webhook` (pública, `--no-verify-jwt`, la llama MP directo desde sus servidores, no un usuario). `crear-pago-mp` ahora manda `notification_url: ${SITE_URL}/functions/v1/mp-webhook?evento_id=...` en cada preferencia — MP la llama sola cada vez que un pago cambia de estado, sin que el comprador tenga que estar en la app. La notificación en sí NUNCA se confía a ciegas (solo trae un id de pago): `mp-webhook` usa el `evento_id` de su propia URL (que nosotros pusimos, no el llamante) para buscar al anfitrión correcto en `mp_credenciales`, vuelve a consultar el pago real contra la API de MP con SU token, y cruza que `pago.metadata.evento_id` coincida con el de la URL antes de activar cualquier boleto — mismo principio que `confirmar-pago-mp`. Solo actúa si `pago.status === "approved"`; si sigue `in_process` o el evento ya no existe, responde 200 sin tocar nada (para que MP no reintente algo que no es un error). El `UPDATE` de boletos es idéntico y por tanto tan idempotente como el de `confirmar-pago-mp` — si el comprador ya se confirmó solo por la vía normal, esta notificación no afecta ninguna fila. Probado en vivo contra pagos reales (uno `in_process`, uno con `evento_id` no correspondiente al pago — rechazado correctamente —, y uno de un evento ya borrado) sin tocar dinero ni datos. **Firma HMAC agregada (2026-07-06):** `mp-webhook` ahora valida el header `x-signature` (manifest `id:...;request-id:...;ts:...;` firmado con HMAC-SHA256 contra `MP_WEBHOOK_SECRET`) antes de procesar cualquier notificación — si no coincide, responde 401 sin gastar la llamada a la API de MP. La verificación real contra la API sigue siendo la garantía de fondo (nadie puede forzar una activación falsa sin un pago real aprobado); la firma es una capa extra de eficiencia para rechazar notificaciones falsas más barato. El secreto se generó y configuró desde el panel de Mercado Pago (Tus integraciones → Webhooks → "Configurar notificaciones", URL `${VITE_SUPABASE_URL}/functions/v1/mp-webhook`, evento "Pagos" únicamente) y se guardó como secret de Supabase (`supabase secrets set MP_WEBHOOK_SECRET=...`). Si el secreto no estuviera configurado, la verificación se omite sin bloquear nada (compatibilidad hacia atrás).

Con el token ya vencido (entrar al sitio tras un rato) la inicialización incluye una renovación por red de cientos de ms, así que React siempre se metía en medio; al recargar, el token ya está fresco y la inicialización termina en microsegundos. **Corregido:** el callback ahora es síncrono (solo `setUser`) y el perfil se pide en un efecto aparte con dependencia `userId` (no el objeto `user`, que cambia de identidad en cada renovación de token); el perfil se guarda como `{ id, nombre, avatar_url }` y se descarta por derivación si el id no coincide con el usuario actual, en vez de limpiarse con un `setState` dentro de un efecto (que rompía `react-hooks/set-state-in-effect`). **Regla para el futuro: nunca poner un `await` a Supabase dentro del callback de `onAuthStateChange`** (es un footgun documentado por Supabase; el refactor "lockless" de auth-js 2.107 **no** lo eliminó — el ciclo es notify-dentro-de-init, no el navigator lock). **Verificado** reproduciendo el bloqueo con la librería real (2.107.0) en Node y en el motor del navegador: patrón viejo → eventos colgados + encabezado vacío; patrón nuevo → ambos cargan. - **Investigación a fondo de los Adelantos de MP (2026-08-08) — 4 respuestas definitivas.** (1) **Desde el objeto `payment` los adelantos NO son detectables, y nunca lo serán:** el objeto solo expone `money_release_date` y `money_release_schema` — **no existe ningún `money_release_status`** (verificado en dos fuentes independientes: el javadoc oficial del SDK de Java de MP y los SDKs de Go). `money_release_date` dice cuándo *debería* liberarse el dinero según la configuración al momento del pago, no si ya se retiró. (2) **PERO sí son detectables vía el Reporte de Liberaciones** (`POST https://api.mercadopago.com/v1/account/release_report` para generarlo, `GET /v1/account/release_report/list` para listarlos; asíncrono, se genera un archivo). Su campo `DESCRIPTION` incluye literalmente **`fee-release_in_advance` ("comisión por adelanto")** — la huella inequívoca de un adelanto —, además de **`payout`** ("extracción en efectivo de dinero disponible") y registros `available_balance` con prefijos `pre_payout_<id>`/`pos_payout_<id>` (saldo antes y después de cada retiro). O sea: adelantos, retiros y saldo son observables, solo que por reporte asíncrono y no por consulta directa del pago. (3) **Cambiar el plazo de liberación NO es retroactivo** — MP documenta que "el nuevo plan se aplicará a las **ventas futuras**". El ataque de "vender con 14 días → cambiar a al instante → sacar → volver a cambiar" **no funciona** sobre dinero ya vendido: cada pago conserva la fecha de liberación que se le asignó al aprobarse. No se encontró ningún límite documentado de frecuencia para cambiar el plazo, pero con la no-retroactividad el punto es irrelevante. (4) **Preautorización (reservar/capturar): existe en MX pero NO sirve para VELA** — `capture_mode: "manual"` en `/v1/orders`, con captura vía `/v1/orders/{id}/capture` y cancelación vía `/v1/orders/{id}/cancel`; **el límite para capturar es de 5 días** desde la creación (después se cancela sola), solo captura total (no parcial), solo tarjetas, y exige migrar de Checkout Pro a Checkout API. Con eventos que se venden semanas antes, 5 días no alcanza. **Descartada con datos, no por sospecha.** Endpoint de saldo directo (`https://api.mercadolibre.com/users/{id}/mercadopago_account/balance`) existe pero es legacy/no documentado en la referencia oficial y no se verificó si acepta el token OAuth de marketplace. **Aplazado, ligado a esto:** comisión VELA 0% en boletos <$50 — prerrequisito obligatorio: guardar `monto_pagado` por boleto al comprar y reembolsar ESO en `gestionar-solicitud` (hoy reembolsa `precio × 1.10` hardcodeado; con 0% activo reembolsaría de más, a costa del anfitrión). **RESUELTO (2026-08-09) con una venta real de $20 + rechazo:** el recibo del ANFITRIÓN muestra `Anulación del cobro −$22`, **`Anulación de cargo Mercado Pago +$5.45`** y **`Anulación cobro comisión por uso de plataforma de terceros +$2`**, con `Total de la operación $0.00`. O sea: **al anfitrión le devuelven las DOS comisiones y termina en cero — un reembolso no le cuesta nada**. Ojo, esto corrige algo que se había dicho antes: MP **sí** devuelve su propia comisión de procesamiento al reembolsar. Del lado de VELA el recibo dice `Devolviste $0` y **no aparece ningún movimiento de saldo** — lo más probable es que el `marketplace_fee` estuviera en "dinero a liberar" y el reembolso cancelara esa liberación antes de aterrizar en el saldo disponible (mismo patrón que los movimientos `Liberación de dinero` / `Venta cancelada` que se ven en la cuenta). **No hay nada que corregir en el código: el reparto ya es justo.** **Implicación no verificada, a tener en cuenta:** si un reembolso ocurre DESPUÉS de que el `marketplace_fee` ya se liberó al saldo disponible de VELA, MP tendría que descontarlo de ahí — no se sabe qué pasa si la cuenta de VELA está vacía (¿falla el reembolso?, ¿saldo negativo?). (b) **Stripe Connect con "destination charges" SÍ hace exactamente lo que se quería** —"Stripe debita las comisiones del saldo de tu plataforma", el anfitrión recibiría el 100% en la misma operación—, pero el usuario probó el alta real y **Stripe México exige RFC personal** ("para satisfacer obligaciones regulatorias"), y el 90% de los universitarios no lo tiene. Ese fue el motivo original por el que el proyecto salió de Stripe. Nota: la pantalla que vio pedía también sitio web, o sea que era el alta de comercio completo; una cuenta creada por API con solo la capacidad `transfers` (configuración "recipient") pediría menos, pero no se llegó a comprobar y el texto del RFC sugiere que aplica a cualquiera que reciba fondos. **Las tres versiones que sí existirían**, por si se retoma: (A) VELA cobra y le paga al anfitrión después (rompe "sin pendientes", y mete custodia de dinero ajeno con la pregunta regulatoria de la Ley Fintech / IFPE); (B) cuota fija + comisión de VELA en cero, con la tarifa de MP mostrada exacta desde antes (cero infraestructura nueva, un día de trabajo — la recomendada); (C) el anfitrión cobra por fuera (efectivo/transferencia) y VELA solo emite y checa boletos: es la única que cumple "sin comisiones de nadie" al pie de la letra, pero pierde el reembolso garantizado. **Dato clave que casi nadie ve:** la comisión de VELA la paga el ASISTENTE (se suma encima del precio), así que el anfitrión hoy ya recibe su precio íntegro menos solo la tarifa de MP — el miedo que motivó todo esto es a un cobro que no sale de su bolsa.
